# Nova verified-result delivery (local contract)

The run service commits the `AUDIT#<runId>` item in the same DynamoDB transaction as a verified result and its leaderboard outbox. This is the durable source for a future Hearso Supabase history row and `nova.run.verified.v1` Kafka topic. The event shape is in `contracts/nova-run-verified.v1.schema.json`. The game ID separates Nova from Trivia; the run ID is the event ID and the per-result deduplication key. A game ID alone is not an idempotency key.

`processAuditBatch` uses the existing `due-outbox` index and `audit_pending`/`audit_processing` statuses. A two-minute conditional lease protects each item. It writes history first, records `historyDeliveredAtMs`, publishes the same event to Kafka, records `kafkaDeliveredAtMs`, then marks the item `audit_delivered`. Destination failures retain the audit item and retry with bounded backoff. A process may die after a destination accepts an event but before the marker is saved, so delivery is **at least once**. The Supabase adapter must upsert by `run_id`; Kafka consumers must deduplicate by `eventId`. A Kafka producer acknowledgement is not a consumer acknowledgement.

The worker receives two destination callbacks. `writeHistory({ event, playerId })` gets the verified event and a private Hearso player key for the account-linked row. `publishKafka(event)` gets only the public-minimized event; names, account keys, credentials, and input transcripts are absent. Both callbacks must resolve only after their destination has durably acknowledged the write. The worker stores a generic failure code rather than exception text, which may contain personal data or transport secrets.

The callbacks are exercised against local fakes and DynamoDB Local. A server-only Supabase history HTTP adapter is defined in the [history contract](supabase-history-contract.md) and tested against a local server; its destination table is not created or connected yet. No broker topic, producer, scheduled worker, cloud credential, or deployed endpoint was added. Before connecting live services, define the account deletion and retention rule for the private `playerId` on the durable audit item; completed audit items currently have no TTL. The [Kafka relay proposal](nova-kafka-relay-contract.md) places publishing in Hearso's existing Supabase-to-Kafka service. That deployment requires changing this worker's completion rule to acknowledge the durable history write, then building the relay with outage, restart, duplicate, and backfill tests. Hearso v1.0.0-beta.9 remains independent of this work.
