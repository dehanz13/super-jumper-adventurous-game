# Nova Kafka relay boundary (proposal after Hearso beta.9)

Nova's verified event has its own schema in `contracts/nova-run-verified.v1.schema.json` and should use a dedicated `nova.run.verified.v1` topic. `eventId` equals the verified `runId`; producers should key messages by that ID and consumers must deduplicate it. The event deliberately excludes the private Hearso `player_id`, display name, credentials, and input transcript.

Hearso's existing Kafka service reads a Supabase Postgres outbox and publishes to its broker on the Hostinger VPS. A Nova path should similarly read durable `nova_run_history` rows from Hearso's existing Supabase project and publish `event_payload` to the dedicated topic. This avoids introducing a direct Lambda-to-VPS broker connection before its network, credentials, and failure recovery are designed. The relay needs a durable publication cursor or per-row acknowledgement in Postgres, at-least-once retries, and a topic consumer deduplication rule using `eventId`. A broker acknowledgement must not be confused with a downstream consumer acknowledgement.

The current local `processAuditBatch` still models two independent sinks: Supabase history and direct Kafka publishing. Before deploying it, adapt the completion rule so the Dynamo audit item is acknowledged after the durable history write, while the Hearso relay owns Kafka retries. The Supabase migration and relay implementation should land together after beta.9, with local broker outage, restart, duplicate, and backfill tests. This document changes no Hearso service, topic, database, or deployed configuration.
